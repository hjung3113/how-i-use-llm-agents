# 회사 도입자를 위한 가이드

Claude Code에 익숙하지 않은 팀에서는 “잘 쓰는 사람의 긴 설정”을 모두 배포하기보다 공통 최소선과 단계별 선택지를 제공하는 편이 안전하다.

## 회사 공통으로 먼저 정할 것

- 어떤 저장소와 데이터에서 사용할 수 있는가
- 어떤 명령과 외부 시스템 접근이 허용되는가
- credential을 어떻게 제공하고 로그에서 어떻게 보호하는가
- local edit, commit, push, PR, merge, deploy의 승인 주체
- AI가 만든 변경에 필요한 사람 review와 CI gate
- 사고나 잘못된 변경을 발견했을 때 중단·보고 경로

이 문서는 보안 정책을 대체하지 않는다. 조직 정책이 이 예시보다 우선한다.

## 권장 도입 단계

```mermaid
flowchart LR
    L1[1단계 · 읽기와 설명] --> G1[통과 조건 · 근거 제시<br/>사실·추측 구분]
    G1 --> L2[2단계 · 작은 로컬 변경]
    L2 --> G2[통과 조건 · 범위 제한<br/>관련 test·사람 diff 검토]
    G2 --> L3[3단계 · 팀 작업 흐름]
    L3 --> G3[통과 조건 · 대화 없이 재현<br/>막을 실패가 명확]
    G3 --> L4[4단계 · 선택적 고급 자동화]
```

### 1단계: 읽기와 설명

- 낯선 코드 설명
- 테스트와 실행 명령 찾기
- read-only diff review
- 문서 탐색

성공 기준: 근거 파일을 제시하고 추측과 확인 사실을 구분한다.

### 2단계: 작은 로컬 변경

- 문서와 테스트
- 좁은 validation
- 되돌리기 쉬운 버그 수정

성공 기준: 범위가 제한되고 관련 test와 사람 diff review가 있다.

### 3단계: 팀 작업 흐름

- Issue acceptance criteria
- project `CLAUDE.md` 또는 `AGENTS.md`
- PR과 CI
- handoff와 독립 review

성공 기준: 특정 숙련자의 대화 기록 없이 다른 사람이 작업을 재현한다.

### 4단계: 선택적 고급 자동화

- subagent 역할 분리
- worktree 병렬 lane
- MCP와 plugin
- headless/CI 실행

성공 기준: 자동화가 막는 실패가 명확하고, 권한·로그·중단·복구가 설계되어 있다.

## 팀에서 피할 것

- 개인의 거대한 `CLAUDE.md`를 검토 없이 전사 배포
- 모든 저장소에 같은 framework 강제
- `--dangerously-skip-permissions`를 입문 기본값으로 사용
- AI가 생성한 test만으로 독립 검증을 대체
- credential과 고객 데이터를 프롬프트나 memory에 기록
- 완료 기준 없이 “알아서 끝까지” 실행

## 첫 팀 실습

같은 작은 Issue를 두 명이 수행한다.

1. 한 명은 자유 형식 프롬프트만 사용한다.
2. 다른 한 명은 목표·범위·완료 조건이 있는 작업 계약을 사용한다.
3. 결과 코드보다 범위 이탈, 재작업 횟수, 검증 가능성을 비교한다.
4. 반복된 유용한 규칙만 project `CLAUDE.md` 또는 `AGENTS.md`로 승격한다.

팀 표준은 가장 많은 규칙이 아니라 가장 적은 반복 설명으로 안전한 결과를 만드는 규칙이어야 한다.
