# 기본 정신모델

## Claude Code는 답변기가 아니라 작업자다

일반 채팅은 주로 텍스트를 반환한다. Claude Code는 권한 범위 안에서 파일을 읽고 수정하고 명령을 실행할 수 있다. 따라서 좋은 요청에는 결과뿐 아니라 작업 경계와 확인 방법이 필요하다.

```text
목표 + 현재 근거 + 허용 범위 + 금지 사항 + 완료 조건 + 보고 형식
```

## 컨텍스트는 세 종류로 나눈다

### 지속되는 규칙

`AGENTS.md`, `CLAUDE.md`에 둔다. 매 작업에서 반복해서 지켜야 하는 규칙이다.

### 제품과 도메인의 진실

`CONTEXT.md`, 제품 문서, 아키텍처, ADR에 둔다. 무엇을 왜 만들고 어떤 불변 조건이 있는지 설명한다.

### 현재 실행 상태

Git, Issue, PR, CI, runtime, `HANDOFF.md`에 있다. 빠르게 변하므로 작업할 때마다 다시 확인한다.

## 프롬프트보다 검증 루프가 중요하다

한 번에 완벽한 프롬프트를 만들려 하지 않는다.

```text
작은 계약 → 결과 → 증거 → 구체적인 finding → focused repair
```

## 모델은 확신을 생성하지 않는다

더 강한 모델도 잘못된 전제, 오래된 문서, 누락된 테스트를 자동으로 해결하지 못한다. 중요한 변경은 다른 역할의 review와 실제 실행 증거를 결합한다.

## 자동화는 위험도에 비례한다

작은 문서 수정에 다중 에이전트 DAG를 만들 필요가 없다. 반대로 데이터 migration이나 외부 publication을 단일 답변만 보고 실행해서도 안 된다.

다음 질문으로 하네스를 고른다.

1. 실패했을 때 되돌리기 쉬운가?
2. 공개 또는 외부 효과가 있는가?
3. 요구사항이 명확한가?
4. 독립적인 작업이 실제로 여러 개인가?
5. 결과를 어떤 증거로 확인할 수 있는가?

## 오케스트레이션은 agent를 많이 부르는 것이 아니다

오케스트레이터의 핵심은 사람을 반복적인 routing loop에서 빼는 것이다.

- 다음에 어떤 workflow가 필요한지 판단한다.
- 필요한 context와 skill을 packet에 넣는다.
- 완료·실패·차단 상태를 직접 확인한다.
- 결과에 따라 repair하거나 graph를 다시 만든다.
- 사람에게는 material decision만 좁게 요청한다.

단순한 작업 목록이나 여러 terminal을 띄우는 것만으로는 충분하지 않다. 상태와 evidence에 따라 다음 행동을 선택하고 terminal condition까지 관리해야 한다.
