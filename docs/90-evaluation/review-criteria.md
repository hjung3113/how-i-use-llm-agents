# 설명자료 리뷰 기준

이 저장소를 공개하거나 확장하기 전에 다음 관점으로 검토한다.

## 1. 독자와 전달력

- 처음 읽는 사람이 2분 안에 핵심 방식을 설명할 수 있는가?
- 적용 절차와 template보다 “왜 이런 방식으로 쓰는가”가 먼저 이해되는가?
- 초급, 중급, 고급의 차이가 도구 수가 아니라 작업 책임의 차이로 보이는가?
- 추상 개념마다 실제 적용 예시나 템플릿이 있는가?

## 2. 사실성과 정직성

- 개인 경험과 일반적인 권장 사항을 구분했는가?
- 특정 도구가 반드시 필요하다고 과장하지 않는가?
- 테스트, review, CI가 각각 무엇을 증명하고 무엇을 증명하지 못하는지 명확한가?

## 3. 구조와 중복

- README는 입문과 내비게이션에 집중하는가?
- instruction file, workflow, harness, toolbox, concept의 책임이 겹치지 않는가?
- 같은 규칙이 여러 파일에서 서로 다르게 반복되지 않는가?

## 4. 실전 사용성

- 예시 파일을 새 저장소에 복사해 바로 수정할 수 있는가?
- 하네스 선택표가 과도한 orchestration을 피하도록 돕는가?
- 각 워크플로우에 시작 조건과 종료 조건이 있는가?
- 실패했을 때 repair 또는 escalation 경로가 있는가?

## 5. 안전과 공유 가능성

- 개인 경로, 프로젝트명, credential, 내부 데이터가 없는가?
- 외부 변경과 파괴적 작업의 승인 경계가 명확한가?
- memory와 로그에 비밀을 남기지 않는가?

## 6. 벤더 중립성과 이동성

- Codex나 Claude 하나에 종속되지 않는 핵심 원칙이 드러나는가?
- 도구 전용 지침이 공통 계약과 분리되어 있는가?
- skill이나 plugin을 제거해도 파일 기반 권위와 검증 루프가 유지되는가?

## 7. 과설계 위험

- 작은 작업에도 DAG, 다중 리뷰, receipt를 요구하지 않는가?
- 각 ceremony가 막는 구체적인 실패가 설명되어 있는가?
- 더 단순한 하네스로 낮추는 기준이 있는가?

## 판정 형식

- `ACCEPT`: 공개 초안으로 충분하며 구체적인 차단 finding이 없다.
- `REVISE`: 범위 안의 수정으로 전달력 또는 정확성을 개선할 수 있다.
- `REJECT`: 핵심 주장, 정보 구조, 안전성에 근본 문제가 있다.

각 finding은 심각도, 위치, 독자 영향, 근거, 최소 수정 방향을 포함해야 한다.
