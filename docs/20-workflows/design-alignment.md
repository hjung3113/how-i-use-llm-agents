# 설계 리뷰와 집중 질문: 머릿속 모델을 문서 권위로 옮기는 과정

내가 구현 전에 설계 문서를 여러 번 리뷰하고 질문하는 이유는 더 그럴듯한 문서를 만들기 위해서가 아니다. **내가 생각하는 제품과 agent가 읽고 구현할 설계 문서 사이의 간극을 줄이는 것**이 목적이다. 이처럼 사람과 문서가 같은 제품을 설명하도록 맞추는 일을 이 장에서는 **설계 정렬(design alignment)**이라 부른다. 정렬된 문서는 제품 질문의 최종 판단 근거인 **설계 권위(authority)**가 된다.

사람은 대화 중에 빠진 전제를 머릿속으로 보충한다. 문서는 그렇게 하지 못한다. 같은 단어를 쓰고 서로 동의한 것처럼 보여도, 실제로는 사용자 흐름·상태 경계·결정 권한을 다르게 이해할 수 있다. 구현을 시작하면 이 차이가 코드와 테스트로 굳어진다. 그래서 되돌리기 어려운 부분은 먼저 문서에서 부딪쳐 본다.

먼저 역할만 쉽게 보면 이렇다.

```text
사용자: 내가 뜻한 제품과 중요한 선택을 설명하고 결정
  → 작성자: 질문으로 빠진 생각을 꺼내 문서에 기록하고 다시 설명
  → 사용자: 문서에서 읽히는 뜻이 내 생각과 같은지 확인
  → reviewer: 그 문서 안의 충돌·누락·반례를 검증
```

reviewer는 사용자의 생각을 대신 정하지 않는다. 질문은 생각을 밖으로 꺼내고, 문서는 그 생각을 함께 볼 수 있게 만들며, review는 기록된 설계가 실제로 그 생각과 일관적인지 확인한다.

## 집중 질문(grilling)이란

**Grilling은 설계를 공격하거나 승인을 받아내는 심문이 아니다.** 한 번에 범위를 좁힌 질문을 반복해, 사용자의 머릿속에만 있던 의도·전제·우선순위를 말과 문서로 드러내는 과정이다. “이 선택이 실패한다면 어디서인가?”, “둘 다 중요할 때 무엇이 먼저인가?”, “그 말에서 제외되는 경우는 무엇인가?”처럼 쉽게 동의하고 넘어갈 부분을 압박해 확인한다. 압박하는 대상은 사람이 아니라 아직 말로 드러나지 않은 전제다.

이 과정이 깨려는 것은 **거짓 합의(false agreement)**다. 같은 문장을 보고 모두 이해했다고 생각하지만 각자 다른 제품을 그리는 상태를 뜻한다. 필요한 것은 질문의 공격성이 아니라, 한 질문이 한 모호함만 다루게 하는 **범위가 정해진 질문(bounded question)**이다.

```text
사용자의 머릿속 생각
  → 좁은 질문으로 밖에 드러냄
  → 사용자가 의도·전제·우선순위를 답함
  → 작성자가 설계 문서에 반영
  → 작성자가 “즉, A이고 B는 아니다”라고 바꿔 말함(paraphrase)
  → 사용자가 자기 생각과 같은지 되짚어 확인(back-check)
  → 공유된 이해로 정렬
```

마지막 두 단계가 중요하다. 답변을 문서에 옮겼다고 정렬이 끝난 것이 아니다. 작성자가 문서를 자기 말로 다시 설명하고 사용자가 확인하는 **되짚어 확인(paraphrase/back-check)**을 거쳐야, 사용자의 생각과 문서에서 읽히는 의미가 양방향으로 맞았는지 알 수 있다. 이렇게 함께 확인된 제품 이해를 **공유된 정신모델(shared mental model)**이라고 한다.

### 짧은 before / after 예시

**Before — 문장은 있지만 생각은 빠져 있다**

> 실패한 작업은 자동으로 재시도한다.

reviewer는 “재시도 횟수와 중단 조건은 무엇인가?”라고 모호함을 드러낼 수 있지만 답을 대신 정하지 않는다. 사용자가 “일시적인 runtime 실패만 한 번 재시도하고, 사용자 입력이 필요한 실패는 자동 재시도하지 않는다”라고 우선순위를 답한다.

**After — 답과 경계가 문서 권위에 남는다**

> runtime의 일시적 실패는 한 번 자동 재시도한다. 같은 실패가 반복되거나 사용자 입력이 필요하면 `blocked`로 남기고 자동 진행하지 않는다.

작성자가 “즉, 복구 가능한 runtime 실패만 한 번이고, 불명확한 실패를 반복 실행하지 않는다는 뜻”이라고 바꿔 말한다. 사용자가 이것이 자기 의도와 같다고 확인하면 그 모호함의 정렬이 끝난다. `ACCEPT`는 이후 reviewer가 이 기록의 일관성을 평가하는 판정이지, 재시도 정책을 정한 결정이 아니다.

## 무엇을 맞추는가

설계 정렬에서 주로 확인하는 것은 다음 네 가지다.

1. **목적과 사용자 계약:** 누구의 어떤 문제가 해결되며, 무엇은 만들지 않는가?
2. **용어와 상태:** 같은 단어가 문서마다 같은 대상을 뜻하고, 상태 전이가 모순되지 않는가?
3. **경계와 권위:** 제품 설계, 구현 계약, delivery plan 중 어느 문서가 무엇을 결정하는가?
4. **trade-off와 실패 조건:** 선택하지 않은 대안과 그 이유, 다시 검토할 조건이 기록됐는가?

문장의 매끄러움보다 서로 다른 독자가 같은 시스템을 그릴 수 있는지가 중요하다. “맞다”라는 답보다 구체적인 반례, 충돌, 빠진 결정이 더 유용하다.

## 내가 사용하는 정렬 루프

```text
현재 설계 권위 확인
  → 내가 이해한 목적·용어·경계를 문서로 표현
  → 한 번에 하나의 중요한 질문으로 grilling
  → 사용자 답변을 문서에 반영
  → 다시 설명하고 사용자가 의미를 확인
  → reviewer가 정렬된 현재 문서를 ACCEPT / REVISE / REJECT로 평가
  → 중요한 제품 선택은 명시된 결정권자가 결정
  → 승인된 결정을 권위 문서에 반영
  → 관련 문서·schema·예시의 정합성 확인
  → 남은 모호함이 없을 때 구현 계획으로 이동
```

질문은 문서에 근거해야 한다. “더 좋은 설계가 있을까?”처럼 넓게 묻기보다 다음처럼 현재 결정이 어디서 깨지는지 확인한다.

- `Result`와 `Verified Result`가 다른 상태라면 누가, 어떤 증거로 전환하는가?
- runtime 실패가 task 종료를 뜻하지 않는다면 재시도와 `blocked` 결정의 주체는 누구인가?
- roadmap의 build 순서가 제품 runtime 순서를 암묵적으로 바꾸고 있지 않은가?
- 문서 두 곳이 같은 용어를 다르게 정의한다면 최종 기준 정의는 어디인가?

한 질문의 답을 문서에 반영하고 되짚어 확인한 뒤 다음 질문으로 간다. 여러 결정을 한꺼번에 묶으면 어떤 전제가 답을 바꿨는지 알기 어렵고, 표면적인 합의가 다시 생긴다.

## 역할은 분리하되 결정권을 자동 위임하지 않는다

사용자는 자신의 의도·전제·우선순위를 답하고 중요한 제품 선택을 결정한다. 작성자는 그 답을 문서에 반영하고 다시 설명한다. 독립 reviewer의 **범위가 정해진 검토(bounded review)**는 정해진 문서와 질문 안에서 반례, 충돌, 빠진 선택을 찾는다. 역할을 나누는 이유는 더 많은 agent를 쓰기 위해서가 아니라 **같은 맹점을 공유하는 자기검증을 피하기 위해서**다.

reviewer의 `ACCEPT`는 현재 문서가 review 계약을 만족한다는 평가일 뿐, 사용자의 생각을 대신하거나 제품 방향을 선택·적용할 권한이 아니다. 범위·사용자 계약·되돌리기 어려운 외부 효과 같은 **중요 결정(material decision)**은 명시된 결정권자에게 남는다. 위임이 승인된 경우에도 질문 범위와 출력 형식을 좁히고, 결정권자가 승인한 내용을 권위 문서에 반영한 뒤 다음 질문으로 이동한다.

## 언제 충분한가

리뷰 횟수로 종료하지 않는다. 다음 상태가 되면 구현으로 넘어간다.

- 목적, 핵심 용어, 시스템 경계와 non-goal을 다른 독자가 일관되게 설명할 수 있다.
- 작성자가 문서를 다시 설명했을 때 사용자가 “내가 뜻한 것이 맞다”고 확인할 수 있다.
- 같은 질문을 다르게 표현해도 사용자 답변과 문서에서 같은 우선순위·경계가 나온다.
- 제품 설계와 구현 계획의 권위가 섞이지 않는다.
- 중요한 선택에는 기각한 대안과 trade-off가 남아 있다.
- reviewer의 구체적인 High·Medium finding이 해결되고 재검토 판정이 `ACCEPT`다.
- 문서, schema, 예시가 같은 계약을 표현한다.

질문 수가 아니라 새 답이 더 이상 핵심 의미를 바꾸지 않고, 되짚어 확인과 독립 review가 같은 모델을 재구성할 때 멈춘다. 반대로 작은 수정, 쉽게 되돌릴 수 있는 선택, 이미 명확한 계약에는 이 과정을 붙이지 않는다. 설계 실패 비용보다 정렬 비용이 커지면 문서 확인과 단일 review로 줄인다.

## 메타프롬프팅·구현·리뷰와의 차이

- [메타프롬프팅](meta-prompting.md)은 흩어진 요청을 실행 가능한 범위와 완료 조건으로 정제한다.
- 설계 정렬은 제품의 의미·용어·경계가 문서에 정확히 남았는지 검증한다.
- 구현 review는 고정된 설계와 diff가 실제로 일치하는지 검증한다.

세 과정은 이어질 수 있지만 서로 대신하지 않는다. 좋은 실행 prompt도 잘못 정렬된 설계를 고치지 못하고, green test도 문서에 빠진 제품 결정을 증명하지 못한다.

메타프롬프팅 중 오래 유지될 제품 의미를 바꾸는 질문이 발견되면 실행 계약 정제를 멈춘다. 그 선택을 설계 정렬과 명시된 결정권자에게 돌려보내고, 갱신된 권위 문서에서 메타프롬프팅을 다시 이어간다.

설계 문서를 어디까지 나눌지는 [제품 설계 문서 분할](../10-foundations/product-design-docs.md), 실제 설계 결정의 진입·종료 조건은 [자주 사용하는 workflow](workflow-patterns.md#4.-설계-결정)에서 이어서 볼 수 있다.
